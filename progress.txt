## Codebase Patterns
- QuipMac is NATIVE macOS SwiftUI. ALL Settings UI is in QuipMac/Views/SettingsView.swift (sidebar NavigationSplitView; panes General/Layouts/Projects/Prompts/Connection/Security/Notifications, each a grouped Form).
- COMPILE ORACLE: ONLY `xcodebuild build -project QuipMac/QuipMac.xcodeproj -scheme QuipMac -destination 'platform=macOS,name=My Mac' -derivedDataPath build`. IDE/SourceKit "Cannot find type X in scope" + "Generic parameter 'T' could not be inferred" are SPURIOUS cross-file noise — IGNORE them, trust xcodebuild.
- DO NOT install (/Applications), ditto, killall, codesign, open, or touch TCC. DO NOT use dev-browser / any browser (native app). A human installs + verifies visually.
- Reusable components already in SettingsView.swift: StatusDot (kinds ok/bad/warn/neutral/busy = tinted SF-symbol + label), connectionHero (focal status: tinted circle glyph + title3 headline + caption subline), grouped Form, SettingsIconTile, SettingsIdentityHeader, ~600pt detail content cap.
- Preserve ALL logic verbatim (importKey + APNs key-id auto-sync, sendTestPush, QR/pairing share, diagnostics bundle, PIN save/regenerate). Reorganize layout/sections ONLY — no behavior change.
- Stay on eb-branch; never push; git add only QuipMac/Views/SettingsView.swift + prd.json + progress.txt (never -A).
- StatusDot usage: `StatusDot(kind: .ok/.bad/.warn/.neutral/.busy, text: "…", mono: false)`. Renders tinted SF glyph + `.body` text in an HStack(spacing:6). Use it for ANY status indicator — replaces ad-hoc `Image(...).foregroundStyle(.green/.red)` + colored Text. NOTE its text is `.body` font, so when a status row also needs a monospaced path/detail, keep that detail as a separate `.caption.monospaced()` Text below the StatusDot rather than cramming it into `text:`.
- Section grouping convention: every Section gets a `header:` Text (even the first one if it isn't a hero) and pure-info prose goes in a `footer:` (`.font(.caption).foregroundStyle(.secondary)`), never a standalone control-less Section.

## 2026-06-22 — US-003 Final craft consistency sweep across all Settings panes
Thread: https://ampcode.com/threads/$AMP_CURRENT_THREAD_ID
- Swept all seven panes for: StatusDot vocabulary, Section header presence, control-less/FYI-only sections, and the ~600pt width cap. The sweep found exactly ONE persistent status row still on an ad-hoc colored glyph.
- CHANGED: `GeneralTab.macPermRow` (Permissions rows) — was raw `Image(checkmark.circle.fill / xmark.circle.fill).foregroundStyle(.green/.red)` + `Text(name)`. Replaced with `StatusDot(kind: granted ? .ok : .bad, text: name)`. This is the exact case StatusDot's own doc comment names as legacy ("a bare SF checkmark (Permissions)"). The `Spacer()` + conditional "Grant" button (openSettingsPane) are unchanged → zero behavior change. StatusDot's `.ok`/`.bad` glyphs (checkmark.circle.fill / xmark.circle.fill) + green/red tint are byte-identical to what was hand-rolled; only the inner HStack spacing (8→6) and imageScale(.medium) differ, both visually negligible.
- DELIBERATELY LEFT (each conversion would either drop a state or violate the verbatim-preserve constraint):
  - `whisperStatusRow` — has a `.downloading` state rendered in BLUE with an `arrow.down.circle` glyph + live "%". StatusDot has no blue/download kind (ok/bad/warn/neutral/busy only), so forcing it to `.busy` would erase the download-progress signal. Its doc comment already says it intentionally "mirrors the StatusDot look" rather than using it.
  - Notifications `testStatus` lines — strings already begin with their own ✓/⚠/✗ glyph and are built inside `sendTestPush` (HARD-CONSTRAINT: preserve verbatim). A StatusDot would double-glyph (its checkmark.circle + the embedded ✓), and stripping the prefix would alter the verbatim strings. Left as colored caption log output (same idiom as ConnectionTab's connectionLogRow).
  - Notifications `importStatus` — single transient feedback caption built in `importKey` (verbatim-preserve); its success variant can embed a ⚠︎ warning, which would clash with a green StatusDot. Left as caption.
  - ConnectionTab Connected-Clients rows — the leading glyph is the DEVICE TYPE (iphone/applewatch/laptopcomputer via clientIcon), not a status indicator; auth state is the trailing "authed/awaiting auth" text. Not a StatusDot candidate.
- VERIFIED no control-less FYI-only Section remains in any pane (US-001 + US-002 already moved pure prose into footers); every non-hero Section carries a `header:`; the two hero sections (Connection `connectionHero`, Notifications `notificationsHero`) share the same headerless `Section { … }` + `.padding(.vertical, 6)` pattern; the 600pt detail-column cap in SettingsView.body is untouched (no edge-to-edge view added).
- LayoutsTab intentionally not Form-ified: it is a List + ContentUnavailableView (native empty-state idiom), has no status indicators and no dead section, so the sweep leaves its structure alone — converting List→Form would change interaction (swipe/selection), a behavior change out of scope.
- Files changed: QuipMac/Views/SettingsView.swift, prd.json, progress.txt.
- **Learnings for future iterations:**
  - A "consistency sweep" story is mostly an AUDIT: read every pane, list the status indicators, and only convert the ones that are genuinely the SAME concept (persistent ok/bad/granted/set state). Resist converting transient log/feedback captions or rows whose leading glyph encodes something OTHER than status (device type, download progress) — those look superficially similar but converting them loses information or doubles glyphs.
  - StatusDot's fixed palette is ok=green / bad=red / warn=orange / neutral+busy=secondary. There is NO blue and NO progress affordance — any row that needs blue (e.g. an active download) or a percentage must stay a custom row, so don't force it into StatusDot for the sake of uniformity.
  - When a status string is produced by a function under a "preserve verbatim" constraint (sendTestPush, importKey), you cannot restyle it via StatusDot without either reparsing/stripping its embedded glyph (alters display) — so leave it. The constraint on the LOGIC effectively pins the PRESENTATION of its output strings too.
  - Same 10 SourceKit "Cannot find … in scope" / "Generic parameter 'T' could not be inferred" diagnostics (lines 57-60, 250) fired again on this edit — documented spurious cross-file noise. `xcodebuild` → `** BUILD SUCCEEDED **`.
